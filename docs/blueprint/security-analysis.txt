ACADEMY PORTAL
security-analysis.txt

1. Security Overview

Academy Portal stores user accounts and controls enrollment state, so the backend must protect identity, authorization boundaries, and write integrity. The main attack surfaces are authentication endpoints, public catalog search endpoints, admin CRUD endpoints, and enrollment transactions.

Security goals:
- only real users can act as themselves
- students cannot escalate to admin powers
- users cannot modify other users' enrollments
- catalog data cannot be tampered with silently
- the service stays available under abusive traffic
- secrets never live in source control

2. STRIDE Threat Model

2.1 Spoofing

Threats:
- forged JWTs
- stolen tokens reused from another device
- credential stuffing on login/register

Mitigations:
- Sign JWTs with a strong secret loaded from environment variables only
- Include exp, iat, sub, role, and jti claims
- Verify algorithm and signature on every protected request
- Keep access tokens short-lived, for example 15 minutes
- Store refresh session hashes in auth_sessions so a stolen database row is not directly reusable
- Hash passwords with bcrypt and configurable work factor
- Apply Redis-backed rate limiting to auth endpoints
- Record last_login_at and suspicious repeated failures

Secret rotation plan:
- Maintain JWT_SECRET_CURRENT and JWT_SECRET_PREVIOUS
- New tokens are signed with the current secret
- Token verification accepts current and previous during the rotation window
- After the grace period, remove the previous secret and force re-login where required

2.2 Tampering

Threats:
- request body manipulation
- SQL injection attempts
- course seat counter corruption during concurrent enrollments
- admin changes without audit trace

Mitigations:
- Validate request bodies before they reach Prisma
- Use Prisma Client only; no string-built SQL in application code
- Use parameterized queries generated by Prisma
- Wrap enrollment and unenrollment in database transactions
- Enforce unique constraints and foreign keys in PostgreSQL
- Append an audit log record for every admin mutation and sensitive auth action
- Reject impossible state transitions such as publish -> draft without an explicit admin workflow

2.3 Repudiation

Threats:
- admin denies making a course change
- user denies enrolling or removing a course
- no trace of which request changed a record

Mitigations:
- Append-only audit_logs table
- Store actor_user_id, entity_type, entity_id, action, before_json, after_json, request_id, ip_address, created_at
- Generate request_id per HTTP request and include it in logs and error responses
- Never update existing audit log rows
- Restrict delete access on audit_logs to database admins only

Suggested audit log shape:
- id: BigInt primary key
- actor_user_id: nullable FK to app_users
- entity_type: enum
- entity_id: BigInt
- action: enum
- before_json: Json
- after_json: Json
- ip_address: varchar(64)
- request_id: varchar(120)
- created_at: timestamptz

2.4 Information Disclosure

Threats:
- leaking password hashes or internal admin data
- returning draft courses to guests
- exposing one student's enrollments to another student
- verbose stack traces in production

Mitigations:
- Never return password_hash, refresh_token_hash, or internal audit payloads to public clients
- Return only published courses to guest/student catalog endpoints
- Resolve current enrollments from JWT subject, not from untrusted userId query params
- Use role-aware serializers for admin-only fields
- Hide stack traces in production responses
- Restrict CORS to approved frontend origins

2.5 Denial of Service

Threats:
- brute force against /auth/login
- repeated public search requests with large limits
- hot-course enrollment storms

Mitigations:
- Redis token bucket per IP and per email for auth endpoints
- Lower threshold on auth routes than on public catalog routes
- Global max page size, for example 100
- Enforce query timeouts and indexed pagination
- Cache first-page catalog results for common filters
- Optionally use short-lived Redis locks on very hot course IDs while PostgreSQL remains the final authority

Recommended rate limits:
- POST /api/auth/login: 5 requests per minute per IP and email pair
- POST /api/auth/register: 3 requests per minute per IP
- GET /api/courses: 60 requests per minute per IP
- Admin write endpoints: 30 requests per minute per token

2.6 Elevation of Privilege

Threats:
- student calls admin-only endpoints
- admin token forged to enroll as student
- horizontal privilege escalation on enrollments

Mitigations:
- requireAuth middleware verifies token and attaches req.user
- requireRole("admin") protects all course/category/teacher mutations
- requireRole("student") protects student enrollment actions
- enrollment queries always scope by req.user.id
- server ignores any userId field sent by clients for protected student operations
- admin and student actions are separated at route level and service layer

RBAC design:
- Guest: read-only public endpoints
- Student: public endpoints + own enrollment endpoints
- Admin: public endpoints + catalog management + analytics + audit access

3. Secret Management

Rules:
- No secrets in source code
- No real secrets in .env.example
- Production secrets live in the deployment platform secret manager
- Startup validation fails if any required secret is missing

Protected values:
- DATABASE_URL
- JWT secrets
- REDIS_URL
- future SMTP or third-party API credentials

Operational practice:
- rotate database passwords on a schedule
- rotate JWT secrets during low-traffic windows
- restrict production secret access to maintainers only

4. Authorization Middleware Design

Middleware chain for protected routes:
1. requestId middleware
2. JSON parser
3. requireAuth
4. requireRole when needed
5. request body validator
6. route handler
7. centralized error handler

Authorization examples:
- GET /api/courses: public
- POST /api/courses: admin only
- PUT /api/courses/{id}: admin only
- DELETE /api/courses/{id}: admin only
- GET /api/enrollments: student only, current user only
- POST /api/enrollments: student only
- DELETE /api/enrollments/{courseId}: student only

5. ORM-Specific Injection Protection

Prisma helps reduce SQL injection risk because:
- values are parameterized instead of string-concatenated
- relations are explicit and typed
- model fields are known at compile time

Still required:
- whitelist sort fields
- reject arbitrary field names in filters
- validate numeric IDs, enums, and pagination tokens
- disallow raw query helpers in normal feature modules

6. Security Logging and Monitoring

Log these events:
- successful and failed login attempts
- token verification failures
- admin create/update/delete/publish/archive actions
- enrollment conflicts and seat-full events
- repeated 401/403/429 responses from the same source

Operational response:
- alert on spikes in failed logins
- alert on sustained 429s from a narrow source range
- alert on repeated admin authorization failures

7. Residual Risks

- JWT remains bearer-token based, so XSS in the frontend could expose tokens
- Password-based auth alone does not stop credential reuse attacks
- Public search endpoints can still be abused if limits and indexes are misconfigured

Recommended future improvements:
- refresh token rotation
- optional MFA for admins
- CSP headers and stricter frontend hardening
- anomaly detection for admin actions
